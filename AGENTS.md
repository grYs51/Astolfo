# Project Guide — Astolfo (nx-stolfo)

A Discord bot ("Astolfo") that tracks server activity (voice sessions, presence/status, messages, minigames) plus an Angular dashboard that visualizes it. Nx monorepo, **yarn** as package manager.

## Architecture map

| Piece | Location | Notes |
| --- | --- | --- |
| Discord bot + REST API | `apps/bot` | One Node process: discord.js gateway client **and** Express API (port `PORT`, default 3000) |
| Angular dashboard | `apps/web` | Angular 21, SSR, standalone components, signals |
| Prisma schema | `libs/models/prisma/schema.prisma` | Postgres, snake_case tables/columns |
| Routed pages | `libs/pages` | shell, login, dashboard, detail-overview |
| Shared UI components | `libs/components` | + Storybook |
| HTTP layer base | `libs/common/api` | `ApiBase.get()` wraps `httpResource` with reactive `() =>` params |
| Auth (frontend) | `libs/auth` | guard, profile store, `USER` token |
| Feature libs | `features/<name>/{data-access,ui}` | e.g. `voice-stats`, `active-servers` |

### Bot internals (`apps/bot/src`)

- **Auto-registration**: `utils/registry.ts` scans `commands/`, `events/`, `slashs/`, `interactions/` at startup. Files must default-export a class extending the matching base class in `utils/structures/` (`BaseCommand`, `BaseEvent`, `BaseSlash`, `BaseInteraction`). Dropping a file in the right folder is all that's needed to register it.
- **In-memory state on the client** (`client/client.ts`): `guildConfigs`, `userConfigs`, `userStatus` (presence cache), `voiceUsers` (open voice sessions, key `` `${guildId}:${memberId}` ``). Voice sessions are **persisted on open**: a row with `ended_on = NULL` is inserted on join and closed on leave / shutdown flush; `voiceUsers` is a pure cache of the open rows. Rows left dangling by a crash are closed at startup (`closeDanglingVoiceSessions`). Statuses work the same way (`utils/handlers/presence/status-save.ts`): a `user_statuses` row is inserted with `ended_at = NULL` when a status starts, closed on the next change or on shutdown (deleted if it lasted under 15 s), and recovered at startup by `closeDanglingStatuses`; each user's writes go through `runSerialized(statusKey(userId))`. Covered by `status-lifecycle.test.ts`.
- **Voice tracking flow**: `events/voiceState/voice-state-update.ts` → `utils/handlers/vc/*`. One `voice_stats` row per state type (VOICE, MUTED, DEAF, VIDEO, STREAMING…) per session, inserted open when the state starts and closed when it ends. Durations are `ended_on - issued_on` in **milliseconds**; SQL aggregations use `COALESCE(ended_on, NOW())` so open sessions count live time, and voice totals must filter `type = 'VOICE'` (the other types overlap it). The other types are used for voice habits (`…/:serverId/voice-habits` leaderboard and `habits` on `getVoiceStatsUser`, SQL in `stats/habits-sql.ts`, shared by the API and the Discord side): they're summed per type with `FILTER` and capped to VOICE. MUTED/DEAF rows already cover server mute/deafen (discord.js `mute` = `serverMute || selfMute`), so never add the SERVER_* rows to them. Handlers for one member run one at a time through `runSerialized(voiceKey(...))` — anything that opens/closes sessions outside `voiceStateUpdate` (`setVc` and the missed-leave cleanup in `events/ready/shard-ready.ts`, which run on every fresh gateway session, and `GuildDelete`) goes through the same queue, and closes always filter `ended_on: null`. Covered by `utils/handlers/vc/voice-lifecycle.test.ts`.
- **API**: `api/index.ts` (express + session + passport-discord), routes in `api/routes/`, feature routes registered in `api/routes/features/index.ts`. `req.db` is injected by `api/utils/middleware/db.ts`.
- **Discord lookups in the API** (membership, server/channel names, member names/avatars) go through `api/utils/discord-directory.ts` — live gateway cache, or fixtures from `dev/mock-discord.ts` when `MOCK_DISCORD=true` (local demo mode: no Discord login, mock OAuth user, seed with `yarn nx run bot:seed`; refused when `NODE_ENV=production`). New handlers should use the directory, not `client.guilds` directly. Statuses have no `guild_id`, so server-wide status views take the member list from `memberIds(guildId)`.
- **Server settings** (`…/servers/:serverId/settings`, `GET` and `PUT` with the whole object): mounted behind `isAuthenticated` + `isServerMember` + `isServerManager` (Manage Server, read from the gateway cache through the directory's `canManage`, since the OAuth tokens aren't stored). Channel pickers offer `postableChannels`: text/announcement channels where the bot has `POST_PERMISSIONS` and the viewer has View Channel and Send Messages, since the welcome text is theirs. Changing the welcome or goodbye message also needs a welcome channel the viewer can post in. The detail page asks `…/servers/:serverId/access` (`{ canManage }`, any member) to decide the settings link. Goodbye posts use the username, not the display name (free text). The page is `overview/detail/:id/settings`. Welcome and goodbye posts (`utils/functions/member-messages.ts`) replace `@member` and only allow the new member's mention, so a message can't ping `@everyone` or roles. Each page save that changes something is logged in `guild_settings_changes` (who, when, field-level from/to; written in the same transaction through `saveGuildConfig`'s `audit` argument) and listed at `…/settings/history`. Chat-command changes aren't logged.
- **Discord-side stats** (`stats/`): SQL for `/stats` and the weekly digest (`queries.ts`, same rules as the API: VOICE rows only, open sessions live) and the text helpers the cards share (`messages.ts`). The digest runs from `utils/schedulers/digest.scheduler.ts`: an hourly check posts any due recap (Mondays 08:00 UTC), and `guild_configs.digest_last_sent_at` stops it posting twice. Configured with `/digest`. Voice streaks (`getStreaks`: consecutive UTC days with 10+ min of VOICE, gaps-and-islands SQL) and lifetime-hour milestones (`milestones.ts`, the hours from the XP rules' `milestoneHours` set on `/admin`) feed the stats card, the digest card and the dashboard profile (`getVoiceStatsUser`).
- **Online status and games on the dashboard**: `…/:serverId/presence` (server pulse: average members online per local hour, night owls, early birds) and `…/users/:userId/presence`; `…/:serverId/games` and `…/users/:userId/games` for rock-paper-scissors. Games against the bot (it cheats) are saved as game type `rock-paper-scissors-astolfo` with only the member's row (Astolfo's move in `metadata`), so every query filtering `ROCK_PAPER_SCISSORS` leaves them out of win rates; they come back separately as `vsAstolfo`. Tic-tac-toe (`slashs/fun/tictactoe.ts`, a 3×3 button board; against Astolfo easy, normal or impossible by minimax) is saved the same way as `tic-tac-toe` / `tic-tac-toe-astolfo`, with each player's cells in `move`; it's not on the dashboard yet. Trivia (`slashs/fun/trivia.ts`) asks the channel questions from Open Trivia DB (`trivia/opentdb.ts`: ten questions per request, five with a category because the API refuses a request it can't fill and the smallest category and difficulty have 6, in one in-memory queue per category and difficulty for every server; questions asked while a request for the same filter is out wait for it, and every request waits until 5 s have passed since the previous one, because the API allows one request per 5 s per IP and answers more with HTTP 429; every failure is answered with a message that names Open Trivia DB). The options `category` (Open Trivia DB's 24, static choices from `CATEGORIES`) and `difficulty` filter the questions; `rounds` (1–10) asks that many in a row with a 5 s pause (round 2 on are follow-ups, each edited by its message id), stops early at a round nobody answers or when Open Trivia DB fails, and ends on a scoreboard card ranked by XP, then right answers, then time on them. Everyone gets one answer per question in 20 s; one game per channel at a time. The question, the result and the scoreboard are cards (`cards/trivia.card.ts`); the result names the winners in `content` without pinging them, and a text-only fallback writes out the CC BY-SA attribution the card otherwise carries. Each question is saved as game type `trivia` with a row per member who answered (`move` = their answer) and `metadata.correctOrder` / `difficulty`, which the `TRIVIA` XP grant reads, plus `metadata.answerMs` (ms from the question showing to each click, shown on the result; XP doesn't use it, and older questions have none). `/trivia-stats [member]` (`slashs/fun/trivia-stats.ts`, SQL in `trivia/stats.ts`) draws one member's answers, 1st places, TRIVIA XP, quickest right answer and best category (the most right answers among categories with 5+ answered). `/geoguess [difficulty] [rounds]` (`slashs/fun/geoguess.ts`, a subclass of the trivia command) runs the same game with a Mapillary street photo and four countries, 30 s per question: `geo/mapillary.ts` picks a photo from the committed pool (`geo/pool.data.ts` and `geo/countries.data.ts`, built once by `yarn nx run bot:geo-pool` with `MAPILLARY_TOKEN`; only image ids are kept and the thumbnail URL is fetched fresh each time), downloads it as a data URI for the card and picks the wrong answers by difficulty (easy other regions, medium same region, hard up to two neighbours). It's saved as game type `trivia` with category `GeoGuess` plus `metadata.imageId`/`country`/`lat`/`lon`/`near`; picking a country that borders the right one is a near miss, saved as `SCORING.TIE` and granted a flat `amounts.triviaNear` (no difficulty factor: hard has two neighbours among the answers) by the same `TRIVIA` grant, under the same daily cap. Without a token `/geoguess` says it isn't set up; every Mapillary failure is answered with a message that names Mapillary, and the result credits the photographer (CC BY-SA); the question doesn't, because a username can name the place. Status SQL cuts each interval into the hours it covers (`onlinePieces` in `voice-stats/presence-sql.ts`); "online" means online, idle or dnd. The voice heatmaps cut sessions the same way (`voiceHeatmapCells` in `voice-stats/heatmap-sql.ts`), so a long session counts in every hour it covers, not just the hour it started.
- **Activity calendar** (GitHub-style graph, last 12 months, always regardless of the page period): `…/:serverId/calendar` and `…/users/:userId/calendar` (one handler, `getActivityCalendar.ts`); daily VOICE minutes (each session cut into the local days it covers, like the heatmaps) and messages in the viewer's `tz`, drawn by `feature-voice-stats-activity-calendar` as weeks × weekdays on the shared heatmap chart.
- **Heatmaps** (`feature-voice-stats-heatmap-chart`, `ui/src/lib/heatmap-chart`): one chart for every day-of-week visual (voice heatmaps, server pulse, activity calendar); the caller picks the resolution. Rows are Monday-first top to bottom: map the API's `dayOfWeek` (Postgres DOW, 0 = Sunday) with `weekdayRow` from `heatmap-grid.ts`.
- **Image cards** (`cards/`): the bot's stats replies are PNG cards, not embeds: `/leaderboard`, `/stats`, `/profile` (numbers from `getMemberProfile`), `/duo` (time with one member, from `getDuo`; public), the rock-paper-scissors result, the trivia question, result and scoreboard, `/trivia-stats`, the 5h voice reminder and the weekly digest. Text inside an image can't ping, so messages that mention someone keep the mention as text `content` next to the card. A card is a pure `(data, theme) => svg` template (`*.card.ts`) built from the blocks in `svg.ts`; `cardFile(svg, name)` makes the Discord attachment; `render.ts` turns it into a PNG with `@resvg/resvg-js`, which only sees the fonts in `assets/fonts` and never fetches URLs, so avatars go in as data URIs (`avatars.ts`, initial as fallback). Colours live in `themes.ts` (`DEFAULT_THEME`). Escape every name with `escapeXml`. To tweak a card or theme, run `yarn nx run bot:card-preview` and look at `tmp/cards/`. The stats card is also a dashboard download (`…/users/:userId/stats.png?period=&theme=&sections=&tz=`, built by `cards/stats-card-svg.ts` like `/stats`): the Card button on the You tab and on member profiles opens `libs/pages/src/card-dialog`, a live preview where the viewer picks the theme and the sections (`STATS_CARD_SECTIONS`; `/stats` draws `DEFAULT_SECTIONS`). The section and theme names are typed in `@nx-stolfo/api-interfaces`. Its sections follow the dashboard's You overview (`libs/pages/src/member-activity`): `totals` is the change headline, both periods as bars, sessions / average session / chat rank, then the level ranking (`getXpNeighbours`: all-time XP, like `…/:serverId/xp-leaderboard` on the dashboard); `streak` is the streak pips and the milestone as a square per hour; `habits` is the five-part meters, with Online from `getMemberOnline`, read only for members of the server since statuses have no guild. Change both together.
- **XP and levels** (`xp/`): an XP ledger, `xp_events`, one row per grant with a `note` saying what earned it. Each row has a unique `key` (`voice:<voice_stats.id>`, `starter:<voice_stats.id>`, `msg:<guild>:<member>:<UTC minute>`, `streak:<guild>:<member>:<day>`, `game:<game_result.id>:<member>`, `trivia:<game_result.id>:<member>`, `reconnect:<guild>:<member>:<other>:<day>`, `welcome:<guild>:<newcomer>:<member>`, `milestone:<guild>:<member>:<hours>`, `weekly:<guild>:<week start>:<member>`), so every grant is `ON CONFLICT DO NOTHING` and running a grant twice adds nothing. VOICE rows are the exception: they're upserted (`upserted` in `grant.ts`, the XP added is the new amount minus the old), because a call still going is graded again. `grantXp` (`grant.ts`) does every source for one member (live) or a whole guild. Messages, streaks, games, trivia, milestones and the weekly top 3 are one `INSERT … SELECT` each. Trivia pays `amounts.trivia` by place (then `triviaCorrect`) times `rules.trivia[difficulty]`, cut at `thresholds.triviaDailyCap` per member per UTC day by a running sum, so a rebuild gives the same rows. The running sum recomputes the day's earlier answers with the current rules, so changing the trivia amounts mid-day moves that day's cap until a recalculation. Voice, starter, reconnect and welcome are worked out in memory: each VOICE session that's still open, or closed but without a final `voice:` row, is cut into a step line (`voice-xp.ts`) of `minute × crowd × deafened × stay × media`. Crowd counts the others in the channel who aren't deafened and aren't bots (`isBot` from the gateway cache). The line's `segments` are saved on the row, so the chart always matches the XP given: `getVoiceStatsUser` attaches each recent session's XP and segments (`xp` on `VoiceSession`), and a recent session on the You tab opens that chart. It also returns the level and `xpSources` (count and XP per source, all time), drawn as the profile's XP card (`feature-voice-stats-xp-card`, tiles from `xpTiles`). Live grants (`awardAndAnnounce` in `level-up.ts`) run only the sources the event can earn (`sources`): `MESSAGE` after a message is saved, `GAME` after a won rock-paper-scissors or tic-tac-toe game against a member (the win streak runs across both), `TRIVIA` for each member who was right once a question's result is saved, and `VOICE_SOURCES` after a session closes (inside the member's `runSerialized` queue). They look back 2 days and post in `guild_configs.level_up_channel_id` when the level went up (`postLevelUp` in `announce.ts`, which posts a member's level once even if a live grant and the sweep both see it). Calls still going are graded every 5 min (`checkpointXp` in `checkpoint.ts`, scheduled with the digest tick at :01, :06, …): each open VOICE row in the database is graded up to now into its `voice:` row, dated now, so XP and level-ups land during the call. Only per-member runs (checkpoint and close, which share the member's voice queue) grade open sessions; the sweep and a recalculation skip them, because a sweep that read a session as open could land after the close and overwrite the final row. A final row is dated at the session's `ended_on`; a row dated anything else is graded again, which also fixes a checkpoint that raced the close. Starter, welcome, streak and milestone (milestones count open time) can land at a checkpoint; reconnect waits for the close, because its query loads both members' whole voice history. A checkpoint skips a guild while `isXpBusy`. The hourly sweep (`sweepXp` in `recalculate.ts`, on the digest tick) grants what the live path missed and posts the level-ups it caused (the weekly top 3, sessions closed at shutdown) by comparing each member's total before and after. Its first run after a start covers all history, which is also the backfill (a guild without XP yet posts nothing); later runs look back from the previous one. Levels are never stored: `levelFor(total, rules)` solves the curve. The rules (`XpRules` in `@nx-stolfo/api-interfaces`, defaults in `xp/rules.ts`) are one global set, tuned on `/admin` and saved in the single-row `xp_rules` table. They're cached in memory (`currentRules()`), loaded at startup (a saved set missing fields added later gets them from the defaults) and replaced by the admin PUT. New amounts only reach new XP (a call still going, or closed but not graded to its end yet, is priced whole with the rules of its next grade). `recalculateXp` rebuilds a guild's ledger in one transaction. It keeps the `voice:` rows of calls still going (the rebuild skips open sessions), which the next checkpoint reprices with the current rules; their starter and welcome rows come back at that checkpoint, at the new amounts. It and each guild's sweep hold an in-memory per-guild lock (`isXpBusy`; the admin action answers 409 while it's held), since both rewriting the ledger at once can deadlock; live grants skip the guild only while it's recalculating (`isRecalculating`), so no level-up compares against a half-built total. `xp/grant.db.test.ts` and `trivia/stats.db.test.ts` run against a real database only when `XP_TEST_DATABASE_URL` is set; CI sets it with a `postgres:17` service and `prisma migrate deploy`.
- **Metrics**: prom-client counters (`api/utils/counter.ts`), exposed at `/api/metrics` (requires `Authorization: Bearer $METRICS_TOKEN`; disabled when unset), snapshotted to the `metrics` DB table every 30s, restored on boot (`load-on-start.ts`, every `discord_*` counter). The same 30 s save upserts the command counters' running totals (prefix, slash, errors; `DAILY_COUNTERS` in `save-on-exit.ts`) for the UTC day into `metric_daily`; a day's usage is its total minus the previous day's. `discord_bot_command_errors_total{name}` counts commands that threw (`base-command.ts`, `base-slash.ts`). `discord_api_requests_total{method,route,status}` and the `api_request_duration_seconds` histogram (no `discord_` prefix, so since the last restart) come from `api/utils/middleware/requestMetrics.ts`; `route` is the route pattern, never the URL, or `unmatched`.
- **Owner admin page** (`/overview/admin`, `features/admin/*`, `libs/pages/src/admin`): `GET /admin/{health,servers,usage,people,web}` in `api/routes/admin/`, each behind `isAuthenticated` + `isOwner` (`req.user.id === OWNER`, 403 otherwise; a test checks every `/admin` route has both). `/auth/status` returns `isOwner`, which drives the web `OwnerGuard` and the navbar link; those only hide the page, the API is the lock. Data: `guild_events` (`join`/`leave`, written by `GuildCreate`/`GuildDelete`; discord.js only fires `GuildCreate` for real joins after ready), `metric_daily`, `page_views`, `user_session.created_at`/`last_login_at` (set at login; NULL = before tracking), and `startupStats` (`utils/startup-stats.ts`: commit, sessions recovered at startup). Actions (`api/routes/admin/actions.ts`, same lock, POST/PUT only because the cookie is `SameSite=lax`, and `/admin/actions/*` takes JSON only (415 otherwise) so a form post from a sibling subdomain can't trigger one; each logs one `Logger.info` line): `POST /admin/actions/digest` (posts one server's digest now through `postDigest` from the digest scheduler, without stamping `digest_last_sent_at`), `…/leave` (`guild.leave()`; `GuildDelete` does the cleanup), `…/close-stuck-sessions` (`closeLeftVoiceSessions` then `setVc`, like ShardReady), `…/broadcast` (text to every digest channel, `allowedMentions: { parse: [] }`), and `PUT /admin/notice`: the maintenance notice, one row in `app_notice`, served to everyone by the public `GET /notice` (the only public route in that folder) and shown as plain text by `lib-notice-banner` in the shell and on `/login`; one shared resource (`NoticeState`) serves the banner and the admin page.
- **Page views**: the shell posts the matched **route pattern** (`overview/detail/:id`, built from the snapshot's `routeConfig` paths) to `POST /features/track` on each navigation to a new path (a `?tab=` change doesn't count), browser only and logged in only. The handler refuses anything that isn't `^[a-zA-Z0-9/:_-]{1,100}$` or contains a 15+ digit run (a Discord id), so ids never land in `page_views` (one row per day, pattern and user).

### Frontend patterns

- Data access: extend `ApiBase`, pass **functions** (`() => this.id()`) for reactive params so `httpResource` refetches on signal change. See `features/voice-stats/data-access/src/lib/voice-stats.api.ts`.
- Stores: `@ngrx/signals` `signalStore` + `withFetchOnInit` (`libs/common/store`).
- Charts: ngx-echarts with tree-shaken `echarts/core` imports per component.
- API response DTOs live in `libs/api-interfaces` (`@nx-stolfo/api-interfaces`), imported by **both** the Express handlers (which type their responses with them) and the Angular data-access libs — changing a response shape breaks the build of whichever side no longer matches.

## Conventions & gotchas

- API handlers use `express-async-handler`; voice-stats routes are mounted behind `isAuthenticated` + `isServerMember` (real guild membership via the Discord directory), so handlers don't re-check access.
- Heavy aggregation belongs in SQL (`$queryRaw` with `Prisma.sql`), not JS reduces — that refactor is done for most endpoints; don't regress it.
- New feature routes must be mounted in `api/routes/features/index.ts` **with `isAuthenticated`**.
- Guild feature toggles are a bitfield (`utils/handlers/settings-handler.ts` `SETTING_FLAGS`).
- New code writes `guild_configs` through `saveGuildConfig(client, guildId, data)` (`utils/functions/set-config.ts`), which also updates `client.guildConfigs` so the bot sees the change at once. The old chat commands, `guild-create.ts` and the digest scheduler still do their own writes.
- Discord IDs are strings everywhere; never parse to number.
- Logger: use `utils/logger.ts` `Logger`, never `console.*`.
- Anything that deletes or rewrites voice, message or game rows (like `bot:seed`) must clear the guild's `xp_events` too: the ledger keys point at those rows, and the sweep would grant the new rows on top of the old XP.
- **Guardrails:** the bot is `strict` TypeScript (prefer narrowing over `!`); lint enforces module boundaries by tag (`type:*` layering, and the bot (`platform:node`) may only import `scope:shared` libs: `api-interfaces`, `models`), `no-console`, and `no-floating-promises` in the bot. New libs need `type:` tags (plus `scope:shared` if the bot uses them). The database is pinned to UTC (migration `database_timezone_utc`, checked at startup by `assertUtcTimeZone`), so `NOW()` matches the UTC timestamps; in new SQL prefer `NOW_UTC` (`voice-stats/presence-sql.ts`), which doesn't depend on the session time zone.
